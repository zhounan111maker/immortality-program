## 第一部分 本地准备

**目的**：先在你的电脑上确认这个项目能正常构建，并且把「终端」和各种必要工具准备好。
这一步不联网上传任何东西，做错了也不会有任何后果。

### 1.1 确认项目还在原地

1. 按键盘上的 **Win 键**（有 Windows 标志的那个键）。
2. 输入 `文件资源管理器`，回车。
3. 在最上面的地址栏里，粘贴下面这一行，然后按回车：

   ```text
   D:\deepseek Work\immortality-program
   ```

4. 你应该会看到这些文件和文件夹：

   ```text
   docs
   node_modules
   public
   scripts
   src
   .gitignore
   index.html
   package.json
   pnpm-lock.yaml
   tsconfig.json
   vercel.json
   vite.config.ts
   ```

**几个关键文件的身份，先认识一下：**

| 文件 | 它是什么 |
| --- | --- |

### 1.2 打开终端

终端就是你**打字**命令的地方。三种打开方式，任选一种：

**方式一（最通用）**

1. 按 **Win 键**。
2. 输入 `powershell`。
3. 在搜索结果里点 **「Windows PowerShell」**。
4. 会弹出一个蓝色或黑色的窗口，最后一行是 `PS C:\Users\你的名字>` 之类的文字，末尾有一个闪烁的光标。这就叫「命令提示符」，可以开始打字了。

**方式二（直接定位到项目文件夹，推荐）**

1. 按 1.1 的方法打开项目文件夹。
2. 点击最上面地址栏的空白处，把里面的路径**全部删掉**。
3. 输入 `cmd`，按回车。
4. 会弹出一个黑色窗口，开头显示 `Microsoft Windows [版本 ...]`，最后一行类似 `D:\deepseek Work\immortality-program>`。这个叫「命令提示符（cmd）」。

**方式三**

按 **Win + X**，在弹出菜单里选 **「终端」** 或 **「Windows PowerShell」**。

**终端使用须知（很重要）**

- 粘贴用 **右键**，或者 **Ctrl + V**（在 PowerShell 里 Ctrl+V 通常可用）。
- 想重新输入，按 **Ctrl + C**（这不会关掉窗口，只是取消当前这一行）。
- 一条命令按回车后，要**等它跑完**再输入下一条。终端「卡住不动」通常是在下载东西。
- **路径里有空格**（`deepseek Work`）时，路径两边的双引号不能省。

**先把当前目录切到项目文件夹**，在 PowerShell 里输入下面这行并回车：

```powershell
cd "D:\deepseek Work\immortality-program"
```

在**命令提示符（cmd）**里则输入：

```text
cd /d "D:\deepseek Work\immortality-program"
```

> `cd` 是「切换到某个文件夹」的命令，`/d` 是 cmd 专用的参数，意思是「允许顺便切换盘符」。PowerShell **不需要** `/d`，写了反而会报错。这是初学者最容易混淆的一点。

**怎么确认切成功了？** 输入下面这行并回车：

```powershell
pwd
```

你会看到一行输出，正是 `D:\deepseek Work\immortality-program`。如果看到的是别的路径，说明上一步没成功。

> **如果出错了**：如果提示 `无法将“pwd”项识别为 cmdlet...`，说明你正在**命令提示符（cmd）**里，而不是 PowerShell。在 cmd 里请用 `cd`（不带参数）来显示当前路径。两种终端功能完全相同，随便用哪个都行。

### 1.3 确认 Node.js 版本

在终端里输入下面这行并回车：

```powershell
node --version
```

**正确的样子**：输出类似 `v22.14.0` 的一行字。

**要求**：本项目的 `package.json` 里写着 `"engines": { "node": ">=20.19.0" }`。
这个下限不是随便定的：本项目使用的 **Vite 8** 要求 **Node.js 20.19+ 或 22.12+**。
版本不够时构建会直接报错：

```
You are using Node.js 20.18.0. Vite requires Node.js version 20.19+ or 22.12+.
```

所以请确认你的输出满足下面**任意一条**：

- `v20.` 开头，且小版本号 **≥ 19**（例如 `v20.19.0`、`v20.20.1`）
- `v22.` 开头，且小版本号 **≥ 12**（例如 `v22.12.0`、`v22.14.0`）
- `v23.` / `v24.` 或更高（都满足）

> **比较省事的做法**：直接安装 **Node.js 22 LTS** 或更高版本，
> 就一定能满足要求，不需要逐个比对小版本号。

> **如果出错了**：
> - 如果提示 `node : 无法将“node”项识别为 cmdlet...` 或者「不是内部或外部命令」，说明**没装 Node.js**，或者装完没有重开终端。
> - 请到 Node.js 官网下载 **LTS 版本**安装（一路「下一步」即可），安装完成后**关掉终端窗口，重新打开一次**，再运行 `node --version`。
> - 如果版本是 `v20.18.0` 这类不满足下限的旧版本，请**重新下载安装新版 LTS**；只升级全局 npm 包是没用的，必须换掉 Node.js 本体。
> - 装 Node.js 的同时会自动装上 npm（另一个包管理器），后面会用到。

### 1.5 如果看到「running scripts is disabled on this system」——先读这一小节

这一小节专门写给一个**非常常见**的 Windows 问题。如果你在运行 `npm` 或 `pnpm` 时看到下面这样的红字，就是它：

```text
npm.ps1 cannot be loaded because running scripts is disabled on this system.
    + CategoryInfo          : SecurityError: (:) [], PSSecurityException
    + FullyQualifiedErrorId : UnauthorizedAccess
```

**原因**：Windows 客户端版的 PowerShell 默认执行策略是 `Restricted`（禁止运行任何脚本），而 npm/pnpm 在 PowerShell 里是以脚本形式调用的，所以被拦住了。微软官方文档说明：Windows 客户端默认是 `Restricted`，而 Windows 的默认策略是 `RemoteSigned`（[关于执行策略 · Microsoft Learn](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies)）。

**解决办法（不需要管理员权限）**：在 PowerShell 里输入下面这行，回车：

```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

如果它问你「是否要更改执行策略?」，输入 `Y` 或 `A` 再回车。

**关键点**：这里用的是 `-Scope CurrentUser`，也就是**只对你自己的账号生效**。需要管理员权限的是 `LocalMachine` 这个作用域，不是 `CurrentUser`，所以你**不需要**用管理员身份运行 PowerShell。

**怎么确认改成功了？** 输入下面这行：

```powershell
Get-ExecutionPolicy -List
```

输出是一张表，其中 `CurrentUser` 那一行应该显示 `RemoteSigned`。

**如果不想改策略，还有两个替代办法（任选其一）**：

1. **改用命令提示符（cmd）**：cmd 不执行 PowerShell 脚本，所以完全不会有这个报错。按 1.2 的「方式二」打开 cmd，把命令原样粘贴进去即可。
2. **显式调用 `.cmd` 版本**：把 `npm install -g pnpm` 写成

   ```text
   npm.cmd install -g pnpm
   ```

> **如果出错了**：如果 `Set-ExecutionPolicy` 本身报「拒绝访问」，说明你的电脑被公司或学校的安全策略统一管理了。这种情况请直接用上面两个替代办法（改用 cmd），不要继续折腾策略。
>
> **绝对不要**把策略设成 `Unrestricted` 或 `Bypass`，`RemoteSigned` 就是官方推荐的安全值。

> **如果出错了**：如果提示端口被占用，说明你之前启动的预览还没关掉。关掉那个终端窗口，或者再按一次 Ctrl + C。

### 1.8 关于 `.npmrc`：**要有一个，但绝不能写镜像源**（请完整读完这一节）

这一节是**整个部署过程中最容易莫名其妙失败的地方**，请务必读完，并且不要只看一半。

**先澄清一个常见误解**：并不是「项目里绝对不能有 `.npmrc`」。
关键在于 `.npmrc` 里**写了什么**。要区分两类配置：

| 配置类型 | 例子 | 该放哪里 | 能不能提交 |
| --- | --- | --- | --- |
| **构建方式** | `node-linker=hoisted` | 项目根目录 `.npmrc` | ✅ **应该提交**，这样本地和 Vercel 构建方式一致 |
| **下载源（镜像）** | `registry=https://registry.npmmirror.com` | 用户级 `%USERPROFILE%\.npmrc` | ❌ **绝对不能提交** |

**本项目的现状**：根目录**有**一个 `.npmrc`，里面**只有**一行 `node-linker=hoisted`。
`.gitignore` 里的注释也解释了原因。**请保持它原样，不要删除，也不要往里加 `registry=`。**

**为什么镜像源不能提交？用大白话说：**

- 在国内，为了下载 npm 包更快，很多人会把自己电脑配置成从一个「国内镜像站」下载，比如 `registry.npmmirror.com`。这个配置一般写在你的**用户级配置文件**里，路径是 `%USERPROFILE%\.npmrc`，它**只影响你自己的电脑**。
- Vercel 的构建**不是**在你的电脑上跑的，而是在 Vercel 的机器上跑的，那些机器在**境外**。

**所以，如果把一个写着镜像源的 `.npmrc` 提交到项目里，会发生两件坏事：**

1. **访问不通或极慢**：构建机要去访问一个为国内优化的镜像站，可能连不上、超时，安装卡死甚至失败。
2. **更糟的是完整性校验失败**：镜像站有时会重新打包（重写）tarball 文件，导致它的内容哈希和 `pnpm-lock.yaml` 里记录的不一致。pnpm 把「完整性校验不通过」当作**硬错误**直接中断构建，报错就是 `ERR_PNPM_TARBALL_INTEGRITY`（[pnpm 错误手册](https://pnpm.io/errors)）。这类错误非常难猜，因为代码本身毫无问题。

**正确做法**：

- 国内镜像**只**留在你用户级的 `%USERPROFILE%\.npmrc` 里。
- 项目里的 `.npmrc` **只保留** `node-linker=hoisted` 这一行，**不要**出现任何 `registry=` 行。
- 如果将来真的必须在 Vercel 上设置 registry，请用项目的**环境变量**，变量名 `NPM_RC`，值是 `.npmrc` 的内容——**而不是改这个文件**（[Vercel 私有 registry 文档](https://vercel.com/docs/private-registry)）。

**怎么检查？** 在终端里输入：

```powershell
Get-Content "D:\deepseek Work\immortality-program\.npmrc"
```

**正确的样子**：输出里能看到 `node-linker=hoisted`，并且**看不到**任何以 `registry=` 开头的行。

> **如果出错了**：
> - 如果这个文件**不存在**了 → 重新建一个，内容就一行 `node-linker=hoisted`。
> - 如果里面出现了 `registry=` 这类镜像地址 → **删掉那一行**，把镜像配置挪到用户级 `%USERPROFILE%\.npmrc`。
> - 如果你在用户级配置文件里也没有镜像，而下载依赖很慢，那再考虑配置镜像 —— 但请确认它写在 `%USERPROFILE%\.npmrc`，而不是项目里。

### 1.9 一个诚实的提醒：中国大陆访问 Vercel 可能较慢

Vercel 官方知识库明确承认，Vercel 托管的站点在中国大陆「may load slowly or fail to load」（可能加载缓慢或无法加载）（[Vercel 官方说明](https://vercel.com/kb/guide/accessing-vercel-hosted-sites-from-mainland-china)）。

这意味着：**部署本身没问题，但你（或你的国内读者）直接访问时体验可能不稳定。** 这不是你做错了什么，是网络链路的问题。如果这一点对你的读者很重要，请把「第九部分 GitHub Pages 备选方案」也读一下，或者考虑在国内的静态托管服务上另放一份。

**为什么强烈建议选 Public？**
Vercel 的免费 Hobby 计划**不能**从「属于 GitHub 组织的私有仓库」部署；如果遇到这种情况，要么把仓库改成公开，要么用一个属于你个人账号的仓库（[Hobby 计划说明](https://vercel.com/docs/plans/hobby)）。个人账号的私有仓库在 Hobby 上是允许部署的，但对你来说，选 Public 最省事，而且这个项目本身就是一份公开的研究纲领。

**为什么仓库必须是空的（不要勾 README）？**
这是一个**工程上的原因**，不是 GitHub 的规定：
如果你勾了「Add a README file」，GitHub 会在远端仓库里替你**先创建一次提交**（包含那个 README 文件）。而你电脑上的项目还**没有**任何提交，两边就是两条互不相关的历史。等你第一次 `git push` 时，Git 会发现「远端有你本地没有的东西」，直接拒绝推送，并报出：

```text
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/...'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

一个**完全空白**的仓库（0 个文件、0 次提交）就不会有这个问题，第一次推送会顺顺利利。第八部分也给出了万一踩到该怎么救。

## 第三部分 把代码推送到 GitHub

**目的**：把 `D:\deepseek Work\immortality-program` 里的文件上传到刚建好的空仓库。

### 3.1 安装 Git for Windows

**先检查有没有装过**。在终端里输入：

```powershell

```

如果输出类似 `git version 2.51.1.windows.1`，说明**已经装好了**，直接跳到 3.2。

如果提示「不是内部或外部命令」，那就装它。

**最快的安装方式**（在终端里输入这一行并回车）：

```powershell
winget install --id Git.Git -e --source winget
```

`winget` 是 Windows 自带的软件安装器，它会自动下载并静默安装 Git（[Git 官方 Windows 下载页](https://git-scm.com/install/windows)）。

如果 `winget` 不可用（提示找不到命令），就用**手动方式**：

1. 打开 [git-scm.com/install/windows](https://git-scm.com/install/windows)。
2. 点 **「Click here to download」** 下载安装包（`Git-2.xx.x-64-bit.exe`）。
3. 双击运行。接下来会出现很多页设置，**下面只讲需要你留意的几页，其他页全部直接点 「Next」**。

**需要留意的第 1 页：默认分支名**

你会看到一个问题：

```text
What would you like Git to name the initial branch after "git init"?
```

- 选项一：**「Let Git decide」**（默认选中）
- 选项二：「Override the default branch name for new repositories」，它右边的输入框里预填了 `main`

**建议：保持默认的 「Let Git decide」。**
原因有两点：一是这份指南后面会明确执行 `git branch -M main`，把分支名改成 `main`，所以这里选什么都会被覆盖；二是 Vercel 判断「生产分支」的顺序是 `main` → `master` → 仓库的默认分支，我们最终一定会得到 `main`，所以不需要在这里改。

**需要留意的第 2 页：PATH 环境变量**

你会看到三个选项，其中一个是：

```text
Git from the command line and also from 3rd-party software
```

它后面标着 **`(Recommended)`**，也是安装程序**默认选中**的。**保持它选中**，直接 Next。
这个选项的作用是：让你能在任意终端里直接敲 `git` 命令。如果选了别的（比如只有 Git Bash），你在 PowerShell 里敲 `git` 会报「不是内部或外部命令」。

**需要留意的第 3 页：凭据管理器**

这一页的选项文字是 **「Use Credential Manager」**。**保持 Enabled（启用）**，直接 Next。
它的作用是帮你记住 GitHub 的登录状态，第一次推送时自动弹出浏览器让你登录（详见 3.5）。

**需要留意的第 4 页：换行符（Line endings）**

安装程序会问你怎么处理「换行符」。这里有三个选项，**它们的效果**分别是：

| 它的效果 | 含义 |
| --- | --- |
| 检出时转成 Windows 风格（CRLF），提交时存成 Unix 风格（LF） | 等价于 `core.autocrlf=true`。本地文件用 Windows 习惯的换行，上传到仓库里统一是 LF |
| 检出时保持原样，提交时存成 Unix 风格（LF） | 等价于 `core.autocrlf=input` |
| 检出和提交都保持原样 | 等价于 `core.autocrlf=false` |

**给 Windows 用户的建议：选第一种**（检出用 Windows 风格、提交统一为 LF）。这样你在记事本里打开的文本文件换行是正常的，而仓库里的文件对 Linux 构建机和协作者也是正常的。

> 说明：上面这张表描述的是**每个选项的效果**，不是安装程序上的按钮原文——安装程序的按钮文字随版本变化，请按「效果」来辨认，不要按字面找。

**安装完成后（这一步非常重要）**：

1. **关闭所有已经打开的终端窗口。**
2. 重新打开一个新终端（1.2 里的任意一种方式）。
3. 重新切换到项目目录：

   ```powershell
   cd "D:\deepseek Work\immortality-program"
   ```

4. 验证：

   ```powershell
   git --version
   ```

**正确的样子**：输出 `git version 2.xx.x.windows.1`。

> **如果出错了**：
> - 装完重新打开终端仍然提示「不是内部或外部命令」→ 说明 PATH 没生效。最省事的办法是**重启一次电脑**；如果还不行，回到安装程序再走一遍，在 PATH 那一页确认选了 `Git from the command line and also from 3rd-party software`。

### 3.3 初始化、提交、推送（核心步骤）

下面这一整段就是**真正把代码传上去**的动作。**请逐行执行，一行一回车，等它跑完再敲下一行。**

#### 在 PowerShell 里

```powershell
cd "D:\deepseek Work\immortality-program"
git init
git add .
git commit -m "初始提交：永生计划研究纲领平台"
git branch -M main
git remote add origin https://github.com/你的用户名/你的仓库名.git
git push -u origin main
```

#### 在命令提示符（cmd）里

```text
cd /d "D:\deepseek Work\immortality-program"
git init
git add .
git commit -m "初始提交：永生计划研究纲领平台"
git branch -M main
git remote add origin https://github.com/你的用户名/你的仓库名.git
git push -u origin main
```

> 两种终端里只有**第一行不同**（cmd 需要 `/d`），其余六行完全一样。
>
> **务必替换**最后第二行里的 `你的用户名` 和 `你的仓库名`，换成 2.3 里记下的真实地址。**不要保留中文占位符**，否则推送会失败。

**每一行在做什么，以及你会看到什么：**

**① `git init`**——在当前文件夹里创建一个 Git 仓库（会生成一个隐藏的 `.git` 文件夹）。

```text
Initialized empty Git repository in D:/deepseek Work/immortality-program/.git/
```

**② `git add .`**——把当前所有文件「加入待提交列表」（`.` 表示当前目录）。因为项目里已经有 `.gitignore`，它里面已经写好了要忽略 `node_modules/` 和 `dist/`，所以这两大块**不会**被上传。

**你会看到什么**：现代 Git 默认没有任何输出。可以用下面这行看看它到底准备提交什么（可选）：

```powershell
git status --short
```

**正确的样子**：一长串以 `A ` 开头的行，列出 `index.html`、`package.json`、`pnpm-lock.yaml`、`vercel.json`、`src/` 里的文件等等；**不应该**出现 `node_modules`。

**③ `git commit -m "初始提交：永生计划研究纲领平台"`**——把待提交的内容记录成一次「提交」。
`-m` 后面引号里的文字是这次提交的说明，写中文完全可以。

**你会看到什么**：

```text
[main (root-commit) 8f3c1a2] 初始提交：永生计划研究纲领平台
 52 files changed, 8421 insertions(+)
```

> **如果出错了**：如果出现类似提示要求你设置身份：
>
> ```text
> *** Please tell me who you are.
> fatal: unable to auto-detect email address
> ```
>
> 说明 3.2 没做。回到 3.2 执行那两条 `git config --global` 命令，然后再运行一次 `git commit -m "初始提交：永生计划研究纲领平台"`。

**④ `git branch -M main`**——把当前分支重命名为 `main`。
**为什么必须做**：Vercel 把 `main` 当作首选的生产分支（顺序是 `main` → `master` → 仓库默认分支）。如果你推上去的分支叫 `master` 或别的名字，虽然通常也能部署，但多一层不确定性（[Vercel Git 文档](https://vercel.com/docs/git)）。
**你会看到什么**：没有输出就是成功。

**⑤ `git remote add origin https://github.com/你的用户名/你的仓库名.git`**——告诉本地 Git「远端仓库在哪」。`origin` 只是给这个远端起的一个代号，习惯叫法。
**你会看到什么**：没有输出就是成功。

**⑥ `git push -u origin main`**——把本地提交上传到 GitHub 的 `main` 分支。`-u` 的意思是「记住这个对应关系」，以后你只要敲 `git push` 就够了。

**你会看到什么**（正常成功的样子）：

```text
Enumerating objects: 60, done.
Counting objects: 100% (60/60), done.
Delta compression using up to 8 threads
Compressing objects: 100% (48/48), done.
Writing objects: 100% (60/60), 220.51 KiB | 3.20 MiB/s, done.
Total 60 (delta 12), reused 0 (delta 0), pack-reused 0
To https://github.com/你的用户名/你的仓库名.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

> **如果出错了**：
> - 报 `remote origin already exists` → 说明你已经加过 origin 了（比如重复执行了命令）。解决办法见第八部分对应行，用 `git remote set-url origin ...` 改地址。
> - 报 `Updates were rejected because the remote contains work that you do not have locally` → 说明远端不是空的（很可能创建仓库时勾了 README）。解决办法见第八部分对应行。
> - 报 `Authentication failed` 或反复要求输入密码 → 看 3.4。
> - 报 `fatal: not a git repository` → 说明你不在项目目录里。重新执行 `cd "D:\deepseek Work\immortality-program"`，然后从 ① 开始。

### 3.4 第一次推送时的登录（GitHub 认证）

GitHub 早就**取消了用账号密码做 Git 认证**的方式（[GitHub 官方认证说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github)）。所以第一次 `git push` 时会要求你验证身份。有两条路，**优先用第一条**。

#### 路线 A（推荐，什么都不用配置）：让 Git Credential Manager 带你登录

Git for Windows 自带了 **Git Credential Manager**（简称 GCM），它是一个帮你管理 GitHub 登录的工具（[项目主页](https://github.com/GitCredentialManager/git-credential-manager)）。

第一次 `git push` 时，会发生这些事：

1. 终端里出现一个弹窗或提示，问你怎么登录 GitHub，通常提供 **「Browser」**（浏览器）选项。
2. 选择浏览器登录后，浏览器会自动打开一个 GitHub 授权页面。
3. 页面上是一个大按钮，写着类似 **「Authorize Git Credential Manager」** 或 **「Continue」**。
4. 点它，然后按提示确认（可能要求你输入 GitHub 密码，或者在你已登录的情况下只是点一下确认）。
5. 浏览器显示 **「Authentication Succeeded」** 之类的成功页面，可以关掉它。
6. 回到终端，你会看到 3.3 里那段推送成功的输出。

**以后就再也不需要登录了**——GCM 会把凭据存在 Windows 凭据管理器里。

> **如果出错了**：如果浏览器没有自动打开，终端里通常会打印一行 `https://github.com/login/device` 和一个 8 位代码。手动在浏览器打开那个网址，把代码填进去，再点授权即可。

#### 路线 B（手动路线）：用 Personal Access Token（个人访问令牌）

如果 GCM 装不上、或者你想手动控制，就用令牌。**令牌就是「一次性的密码」**。

1. 在浏览器里登录 GitHub。
2. 点右上角头像 → **「Settings」**。
3. 左侧菜单拉到最下面 → **「Developer settings」**。
4. → **「Personal access tokens」** → **「Fine-grained tokens」**（GitHub 官方现在推荐使用 fine-grained 细粒度令牌；[GitHub 官方令牌文档](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)）。
5. 点 **「Generate new token」**。
6. 填写：
   - **「Token name」**：随便写，例如 `deploy-immortality-program`。
   - **「Expiration」**：有效期。**令牌会过期**，可以自定义天数（也可以选择不过期，但不建议）。
   - **「Repository access」**：选 **「Only select repositories」**，然后勾选你刚建的那个仓库。
   - **「Permissions」** → 展开 **「Repository permissions」** → 找到 **「Contents」**，设为 **「Read and write」**。
7. 点 **「Generate token」**。
8. 页面上会出现一串以 `github_pat_` 开头的长字符串。**立刻复制它**——离开页面后**再也看不到**了。

**怎么用**：下一次 `git push` 提示输入用户名密码时：

- `Username for 'https://github.com':` → 输入你的 GitHub 用户名
- `Password for 'https://你的用户名@github.com':` → **粘贴刚才那串令牌**（注意：这里粘贴时屏幕上不会显示任何字符，这是正常的，粘完直接回车）

> **关于 fine-grained 令牌的一个已知限制**：GitHub 文档指出，细粒度令牌在「向你不属于其成员的公开仓库贡献代码」这种场景下有功能限制。对**你自己账号下的个人仓库**来说，按上面的方式给「Contents: Read and write」权限就完全够用。
>
> **如果出错了**：
> - 报 `remote: Permission to ... denied` → 令牌权限不够，或者有效期已过。重新生成一个，确保勾了 `Contents: Read and write` 并且选中了正确的仓库。
> - 报 `Authentication failed` 而你又确定令牌没错 → 可能是旧凭据被缓存了。打开 Windows 的「凭据管理器」（开始菜单搜索「凭据管理器」）→ 「Windows 凭据」→ 找到 `git:https://github.com` → 删除它，再重新推送。

### 3.5 回 GitHub 确认文件真的上去了

1. 回到浏览器，打开你的仓库页面：`https://github.com/你的用户名/你的仓库名`。
2. **按 F5 刷新。**

**你会看到什么（正确的样子）**：

- 页面中间出现一个文件列表，包含 `docs`、`public`、`scripts`、`src` 这些文件夹，以及 `.gitignore`、`index.html`、`package.json`、`pnpm-lock.yaml`、`tsconfig.json`、`vercel.json`、`vite.config.ts` 这些文件。
- 页面上方显示一行提交说明：**「初始提交：永生计划研究纲领平台」**。
- 分支下拉框显示 **`main`**。

**请特别确认这两件事：**

| 必须有 | 必须没有 |
| --- | --- |
| `pnpm-lock.yaml` | `node_modules` |
| `vercel.json`（在**根目录**，和 `package.json` 同一层） | `dist` |

- **`pnpm-lock.yaml` 必须有**：Vercel 靠它判断「这个项目用 pnpm」，并自动运行 `pnpm install`，还会挑一个与锁文件匹配的大版本（[Vercel 包管理器文档](https://vercel.com/docs/package-managers)）。
- **`node_modules` 和 `dist` 必须没有**：它们已经在 `.gitignore` 里被忽略。上传它们会让仓库变得巨大且毫无意义。

> **如果出错了**：如果 `vercel.json` 出现在 `dist/` 或其他子目录里，那部署时会失效。`vercel.json` 的正确位置是**项目根目录**，也就是和 `package.json` 紧挨着的那一层。

**你会看到什么**：进入 Vercel 的 **Dashboard**（控制台），页面上方有 **「Add New...」** 和 **「New Project」** 之类的按钮，中间提示你还没有任何项目。

### 4.2 导入你的仓库

1. 在 Vercel 控制台的**右上角**，点 **「Add New...」**，然后选 **「Project」**（老界面里是直接点 **「New Project」**，位置在右上角）（[Vercel 官方入门文档](https://vercel.com/docs/getting-started-with-vercel)）。
2. 页面会列出你 GitHub 上的仓库，标题类似 **「Import Git Repository」**。
3. 找到你的仓库（例如 `你的用户名/immortality-program`）。
   - 如果列表是空的：点 **「Adjust GitHub App Permissions」**（或 **「Configure GitHub App」**），在 GitHub 页面里授权 Vercel 访问你的仓库（可以选「All repositories」或只勾这一个），然后回到 Vercel 刷新。
4. 点仓库右侧的 **「Import」** 按钮。

**你会看到什么**：进入一个标题类似 **「Configure Project」**（配置项目）的页面。**先别急着点 Deploy**，下一节的内容就在这个页面上。

### 4.3 配置页面上的每一个字段（这是全篇最关键的一节）

Vercel 把项目的构建设置放在 **Settings → 「Build and Deployment」** 里，字段名是固定的这几个：**Framework Preset**、**Root Directory**、**Build Command**、**Output Directory**、**Install Command**、**Node.js Version**（[Vercel 构建配置文档](https://vercel.com/docs/builds/configure-a-build)）。

导入时看到的配置页，字段名与此一致（部分字段折叠在 **「Build and Output Settings」** 里）。**本项目应该填的值如下：**

| 字段 | 本项目填什么 | 说明 |
| --- | --- | --- |
| **Project Name** | 例如 `immortality-program` | 它决定你的默认网址：`https://immortality-program.vercel.app`。必须是全小写英文/数字/连字符，且**全球唯一**，被占了就换一个 |
| **Framework Preset** | **`Vite`** | 选 `Vite` 后 Vercel 会自动套用 Vite 的标准构建参数（[Vercel Vite 文档](https://vercel.com/docs/frameworks/frontend/vite)） |
| **Root Directory** | **留空 / 保持默认**（本项目的推荐情况，详见 4.4） | 项目文件所在的目录。留空表示「仓库根目录就是项目根目录」 |
| **Build Command** | `pnpm run build`（也可以让它自动检测） | 本项目 `package.json` 里 `build` 的定义是 `tsc --noEmit && vite build` |
| **Output Directory** | `dist` | Vite 默认把构建产物放在 `dist` 文件夹，本项目 `vite.config.ts` 里也显式写了 `outDir: 'dist'` |
| **Install Command** | **留空（让它自动检测）** | ⚠️ **千万不要填 `pnpm install`**，原因见 4.5 |
| **Environment Variables** | **不需要填任何东西** | 本项目没有任何需要保密的配置 |
| **Node.js Version** | **不用动**（保持默认） | 默认是当前最新的 LTS，撰写研究资料时是 24.x；可选 24.x / 22.x / 20.x。`package.json` 里的 `engines.node` **会覆盖**这个下拉框。本项目要求 `>=20.19.0`（因为 Vite 8 要求 Node 20.19+ / 22.12+），Vercel 的默认版本满足它，所以不用改（[Vercel Node.js 版本文档](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)） |

> 顺便说明：本项目的 `vercel.json` 里也已经声明了 `framework`、`buildCommand`、`outputDirectory`。**面板里的值请保持和文件一致**（也就是按上表填写或者留空用自动检测），这样两处不会互相矛盾。

### 4.4 ⚠️ 最大的坑：Root Directory

Vercel 官方文档对 Root Directory 有一句非常重要的说明：

> "Your app will not be able to access files outside of that directory. You also cannot use `..` to move up a level."
> （你的应用无法访问该目录之外的文件，也不能用 `..` 往上一层。）
> —— [Configure a Build · Vercel](https://vercel.com/docs/builds/configure-a-build)

这句话的白话版：**Root Directory 之外的东西，Vercel 在构建时完全看不到。** 如果它填错了，Vercel 会「找不到 `package.json`」或者「找不到 `vercel.json`」，构建直接失败。

而且要注意：**这个设置只对「下一次部署」生效**。改完它，必须重新部署一次（最简单的方式是照第六部分再推一次代码）才会看到效果。

**改它的位置**：进入项目 → **「Settings」** → **「Build and Deployment」** → **「Root Directory」** → 填写 → 点 **「Save」**。

**你的项目应该怎么填？分两种情况：**

#### 情况 A：你把 `immortality-program` **里面**的内容作为仓库根目录（本指南推荐，也是第三部分的做法）

- 表现：在 GitHub 仓库首页，你**直接**就能看到 `package.json`、`vercel.json`、`src/`。
- **Root Directory 必须留空。**
- 因为 `package.json` 就在仓库的最顶层，此时的「仓库根目录」和「项目根目录」是同一个。

#### 情况 B：你的仓库里还有别的文件夹，`immortality-program` 只是其中一个子目录

- 表现：在 GitHub 仓库首页，你看到的是 `immortality-program`、`other-thing` 这样的文件夹，**看不到** `package.json`。
- **Root Directory 必须填 `immortality-program`**（就是那个装着 `package.json` 的文件夹的名字）。
- 如果这里留空，Vercel 会在仓库最顶层找 `package.json`，找不到就报错，构建在第一步就失败。

> **一句话判断法**：打开你的 GitHub 仓库首页，**`package.json` 在哪一层，Root Directory 就填哪一层的相对路径；如果它就在最外层，就留空。**

**如果出错了**：

- 构建日志里出现 `Could not find a package.json`、`No package.json found`、`Error: The specified Root Directory does not exist` → 说明 Root Directory 填错了。按上面两种情况重新判断，改完**记得 Save**，然后重新部署一次。
- 改了设置但什么都没变化 → 别忘了「只对下一次部署生效」，必须触发一次新部署。

### 4.5 ⚠️ 千万不要设置 Install Command（pnpm 版本会被降级）

导入页面和设置页都有一个 **「Install Command」** 字段。**请保持它为空。**

Vercel 官方文档明确警告过这件事：

> "When using an override install command like `pnpm install`, Vercel will use the oldest version of the specified package manager available in the build container. For example, if you specify `pnpm install` as your override install command, Vercel will use pnpm 6."
> （当你使用 `pnpm install` 这类覆盖式安装命令时，Vercel 会使用构建容器里**该包管理器最老的版本**。例如把 `pnpm install` 填成覆盖命令，Vercel 就会用 **pnpm 6**。）
> —— [Package Managers · Vercel](https://vercel.com/docs/package-managers)

pnpm 6 太老了，会和本项目的 pnpm 9 锁文件、以及 Vite 8 的工具链冲突，直接构建失败。

**正确的做法是：什么都不填，只把 `pnpm-lock.yaml` 提交上去。** Vercel 会通过锁文件自动识别包管理器（[Package Managers · Vercel](https://vercel.com/docs/package-managers)）：

| 仓库里的锁文件 | Vercel 自动执行的安装命令 |
| --- | --- |
| `pnpm-lock.yaml` | `pnpm install` |
| `package-lock.json` | `npm install` |
| `yarn.lock` | `yarn install` |
| 没有任何锁文件 | 默认用 `npm` |

本项目的 `pnpm-lock.yaml` 已经在第三部分推送成功了，所以 Vercel 会自动跑 `pnpm install`，并挑一个匹配的大版本。

> **如果出错了**：如果构建日志里出现 `pnpm/6.x.x` 之类的版本号，或者报 `ERR_PNPM_OUTDATED_LOCKFILE`，先检查你是不是在某个地方填了 `pnpm install` 作为 Install Command（导入页、Settings → Build and Deployment、以及 `vercel.json` 三处都检查一遍），把它清空再重新部署。

**逐个字段解释：**

| 字段 | 作用（白话） |
| --- | --- |
| `"$schema"` | 只是一行「给我用的编辑器看的提示」，告诉编辑器这份文件的规范定义在哪。**不影响部署**，可以原样保留 |
| `"framework": "vite"` | 声明这是 Vite 项目，让 Vercel 套用 Vite 的标准构建流程 |
| `"buildCommand": "pnpm run build"` | 构建时执行的命令。它对应 `package.json` 里的 `build`，也就是「先做 TypeScript 类型检查，再打包」 |
| `"outputDirectory": "dist"` | 构建产物在 `dist` 文件夹里，部署时把**这个文件夹的内容**发布出去 |
| `"trailingSlash": false` | 网站的规范地址**不带**结尾斜杠（是 `/protocols/p01`，不是 `/protocols/p01/`）。显式写出来是为了让行为明确，不依赖平台默认值 |
| `"rewrites"` | **最关键的一条**，下面单独讲 |
| `"headers"` | 给不同路径附加 HTTP 响应头，全部在下面单独讲 |

#### `rewrites` 是干什么的（为什么它必须有）

用一句话说，这条规则做的事是：

> **除了静态资源以外的任何路径，都交给 `index.html`，由前端路由自己处理。**

你的网站是 **SPA（单页应用）**，路由是在浏览器里用 `history.pushState` 实现的：`/protocols/p01`、`/blog/post-what-is-plan` 这些地址看起来很「像文件夹」，但服务器上**根本没有对应的文件**——只有一个 `index.html`。

所以：

- 用户在首页里点链接跳到 `/protocols/p01` 时，**不会**再去问服务器（是 JavaScript 在本地换页面），一切正常。
- 但如果你把 `https://你的站点/protocols/p01` 这个地址**直接粘贴到一个新标签页**，或者刷新这个页面，浏览器就会**真的去问服务器**要 `/protocols/p01` 这个文件。服务器找不到 → 返回 **404 页面**。这就是「深链接会 404」。
- 加了这条 `rewrites` 之后，服务器遇到这种找不到的路径，就不再报 404，而是返回 `index.html`；浏览器拿到 `index.html` 和 JavaScript 后，前端路由再看一眼地址栏，把协议页面渲染出来。**深链接就正常了。**

规则里的那串正则，就是「哪些路径**不要**被改写」的排除清单：`assets/`（构建出来的 JS/CSS）、`icons/`（PWA 图标）、`archive/`（归档文件）、`sw.js`（Service Worker）、`manifest.webmanifest`（安装清单）、`robots.txt`、`sitemap.xml`、`offline.html`、`favicon.svg`。**这些必须原样返回给浏览器**——如果连 `sw.js` 都被改写成 HTML，离线功能和安装功能就全废了（第五部分会教你怎么亲手验证这一点）。

规范写法参考 Vercel 官方 Vite 页面（它给出的正是用 `rewrites` 的现代写法，**不是**老的 `routes` + `handle: filesystem` 写法；Vercel 文档把 `rewrites`/`redirects`/`headers` 描述为 `routes` 的「更简洁的替代方案」）（[Vercel Vite 文档](https://vercel.com/docs/frameworks/frontend/vite)、[vercel.json 配置文档](https://vercel.com/docs/project-configuration/vercel-json)）。

> **如果出错了**：深链接还是 404 → 99% 是这件事之一：① `vercel.json` 不在项目根目录（例如被放进了 `dist/`）；② Root Directory 填错了，导致 Vercel 读不到根目录的 `vercel.json`；③ 改完文件后忘了 `git push`。三条都排查一遍。

#### `headers` 是干什么的（每一项的作用）

| 路径 | 头 | 作用 |
| --- | --- | --- |
| `/assets/(.*)` | `Cache-Control: public, max-age=31536000, immutable` | 构建出的 JS/CSS 文件名里带内容哈希，**内容变了文件名就变了**，所以可以放心让浏览器缓存一年，第二次访问极快 |
| `/icons/(.*)` | `Cache-Control: public, max-age=604800` | 图标缓存 7 天，减少重复下载 |
| `/manifest.webmanifest` | `Content-Type: application/manifest+json; charset=utf-8` | 明确告诉浏览器这是「应用安装清单」。有些环境会用错类型，导致浏览器不认，安装图标就不出现 |
| `/manifest.webmanifest` | `Cache-Control: public, max-age=0, must-revalidate` | 每次校验清单是否有更新，避免改了清单却长期不生效 |
| `/sw.js` | `Content-Type: application/javascript; charset=utf-8` | Service Worker **必须**以 JavaScript 的 MIME 类型注册，否则浏览器直接拒绝注册（[MDN: register()](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)、[MDN: 使用 Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)） |
| `/sw.js` | `Cache-Control: public, max-age=0, must-revalidate` | 让浏览器每次都重新检查 `sw.js` 有没有更新，否则你会一直卡在旧版本 |
| `/sw.js` | `Service-Worker-Allowed: /` | 允许这个 Service Worker 的作用域覆盖整个站点根路径 `/` |
| `/(.*)`（全站） | `X-Content-Type-Options: nosniff` | 禁止浏览器「猜」文件类型，防止某些类型混淆攻击 |
| `/(.*)`（全站） | `X-Frame-Options: SAMEORIGIN` | 禁止别的网站用 iframe 把你的站点套进他们的页面 |
| `/(.*)`（全站） | `Referrer-Policy: strict-origin-when-cross-origin` | 跳到别的网站时不泄漏完整地址，只带域名 |
| `/(.*)`（全站） | `Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()` | 明确关闭摄像头、麦克风、定位等能力申请；也对旧的「兴趣组」追踪表态 |

### 4.9 PWA：为什么部署后就能「安装成 App」

本项目用 `vite-plugin-pwa` 配置了 PWA（渐进式 Web 应用）。部署完成后：

- 用 **Chrome 或 Edge** 打开你的正式网址，地址栏**右侧会出现一个「安装」图标**（形状像一个显示器带一个下箭头，或者一个小方块加号）。
- 点它，浏览器会问「要安装「永生计划 · 研究纲领平台」吗？」，点 **「安装」**。
- 装完后，它会像普通软件一样出现在开始菜单里，独立窗口打开，**地址栏消失**，看起来就是一个 App。
- 手机上（Android Chrome / iOS Safari）也可以「添加到主屏幕」。

**为什么能安装？** 官方（MDN）给出的前提条件包括：站点通过 **HTTPS** 提供（或 localhost），并且清单里提供了 **192px 和 512px 的图标**（[MDN: 使 PWA 可安装](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)）。本项目两样都满足：

- Vercel 自动提供 HTTPS，而 `.vercel.app` 域名本身还在浏览器的 HSTS 预加载列表里。
- 项目的 `vite.config.ts` 里已经声明了 `icon-192.png`、`icon-512.png`、以及一个 maskable 图标。

另外一个容易被忽略的细节：清单里的 `start_url` 和 `scope` 在本项目里**都**是 `"/"`。MDN 说明，`scope` 必须**包含** `start_url`，否则就会静默回退到默认值（[MDN: manifest 的 scope](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/scope)）。两个都写 `"/"` 就永远不会踩这个坑。

## 第五部分 验证是否成功

**部署成功 ≠ 一切正常。** 请按下面的清单**逐条亲手验证**。每一条都告诉了你「正确的样子」。

### 5.1 逐条检查清单

1. **首页能打开**
   在浏览器新标签页里，粘贴 Vercel 给你的网址（形如 `https://immortality-program.vercel.app`），回车。
   ✅ **正确的样子**：网站正常显示，中文排版正常，地址栏有**小锁**图标（HTTPS）。
   ❌ 如果显示 Vercel 的 404 页面或者「Deployment Not Found」，检查网址是否复制完整。

2. **深链接能用（这一条证明 `rewrites` 生效了）**
   在新标签页里，直接粘贴这个地址并回车（把域名换成你自己的）：

   ```text
   https://你的域名.vercel.app/protocols/p01
   ```

   ✅ **正确的样子**：显示的是**协议 p01 的页面**，而不是 404。
   ❌ 如果显示 404 → 说明 `rewrites` 没生效。回到 4.6 的「如果出错了」，检查三件事：`vercel.json` 是否在项目根目录、Root Directory 是否填错、改动是否已 `git push`。

   再试一个博客深链接：

   ```text
   https://你的域名.vercel.app/blog/post-what-is-plan
   ```

   ✅ 同样应该显示文章页面。

3. **`/sw.js` 返回的是 JavaScript 代码（重要！）**
   在新标签页里打开：

   ```text
   https://你的域名.vercel.app/sw.js
   ```

   ✅ **正确的样子**：一屏 JavaScript 源码，通常以 `importScripts(...)` 之类的内容开头，能看到 workbox 相关的代码。
   ❌ **如果显示的是你的网站界面（HTML）**，说明 `rewrites` 把 Service Worker 也吞掉了——离线功能和安装功能都会失效。请检查 `vercel.json` 里 `rewrites` 的排除清单是否包含 `sw\\.js`。

   **为什么必须亲手检查这一条**：Vercel 的公开文档**没有**说明「静态文件」和「rewrites」的先后顺序。我们无法从文档确定 Vercel 一定先返回真实存在的静态文件、再应用改写规则。所以这一项不能靠推理，只能**实测**。

4. **`/manifest.webmanifest` 返回的是 JSON**

   ```text
   https://你的域名.vercel.app/manifest.webmanifest
   ```

   ✅ **正确的样子**：一段 JSON，包含 `"name": "永生计划 · 研究纲领平台"`、`"short_name"`、`"start_url": "/"`、`"scope": "/"`、以及 `icons` 数组。

5. **浏览器提供「安装」入口**
   用 Chrome 或 Edge 打开首页。
   ✅ **正确的样子**：地址栏右侧出现安装图标（可能需等几秒钟，或先在页面里点几个链接浏览一下）。
   ❌ 如果没出现：按 **F12** 打开开发者工具 → 顶部选 **「Application」** → 左侧 **「Manifest」**，看有没有红色错误提示。

6. **Service Worker 已激活**
   在首页按 **F12** → 顶部选 **「Application」** 标签 → 左侧找到 **「Service Workers」**。
   ✅ **正确的样子**：列表里有一条记录，状态是 **「activated and is running」**，作用域是 `https://你的域名.vercel.app/`。
   ❌ 如果状态是 `waiting to activate` 或列表为空：先点一下 **「Update on reload」** 再刷新页面；或者确认第 3 条（`/sw.js`）是正常的。

7. **离线也能看（证明离线缓存真的在工作）**
   两种做法任选一种：
   - **DevTools 做法**：F12 → **「Application」** → 左侧 **「Service Workers」** → 勾选 **「Offline」**，然后刷新页面。
   - **物理做法**：把电脑的 Wi-Fi / 网线断开，然后刷新页面。

   ✅ **正确的样子**：页面内容**照常显示**（因为已经被 Service Worker 缓存），而不是浏览器的「无法连接互联网」错误页。
   验证完记得把 Offline 勾选**取消**，或重新连上网络。

8. **手机上打开也正常**
   用手机浏览器（建议先在 Wi-Fi 下）打开同一个网址。
   ✅ **正确的样子**：文字大小合适，不需要左右拖动；页面**底部有导航栏**；可以点开协议列表并进入详情。
   ✅ 可选：在手机浏览器的菜单里选 **「添加到主屏幕」**，然后从桌面图标打开，应该没有浏览器地址栏。

> **如果任何一条不通过**：把「不通过的是第几条」+「屏幕上实际显示了什么」+「DevTools 里的红色报错（F12 → Console 标签）」这三样信息记录下来，对照第八部分的表格，或交给你的 AI 助手/开发者。

### 5.2 关于验证的一个诚实说明

第 3 条（`/sw.js`）之所以要**用眼睛看**，是因为 Vercel 的文档没有规定「静态文件优先」还是「rewrites 优先」。我们只知道 `rewrites` 规则本身是对的（它明确排除了 `sw.js`），但真正的执行顺序只能靠实测确认。

如果第 3 条不通过（`/sw.js` 返回了 HTML），说明 `rewrites` 抢在了静态文件前面。此时可以参考的补救方向是：把 `sw.js` 的排除规则调整得更明确，或者改用 Vercel 的 `routes` 写法显式声明「先查文件系统，再回退到 index.html」。**修改后务必重新部署并再次检查第 3 条。**

## 第六部分 以后如何更新

这是这套方案最舒服的地方：**以后你只需要推送代码，剩下的 Vercel 全自动做完。**

### 6.1 更新三步曲

1. 在本地修改内容（比如编辑 `src/content/posts.ts` 加一篇研究笔记）。
2. 在本地先自检一遍，确保推上去的东西是好的：

   ```powershell
   cd "D:\deepseek Work\immortality-program"
   pnpm run build
   ```

   ✅ 看到 `✓ built in ...` 就说明没问题。

3. 提交并推送：

   ```powershell
   git add .
   git commit -m "新增：关于计划可证伪性的研究笔记"
   git push
   ```

   （第一次推送时用了 `-u origin main`，之后直接 `git push` 即可。）

**接下来会自动发生什么**：

- Vercel 检测到 GitHub 上 `main` 分支有了新提交，**自动开始一次新的构建和部署**（[Vercel Git 文档](https://vercel.com/docs/git)）。
- 你可以在 Vercel 控制台的项目页面里看到一条新的部署记录，状态从 **Building** 变成 **Ready**。
- `Ready` 之后，你的网址上就是新版本了。**同一个网址不会变**，不需要重新导入项目。

> **如果出错了**：
> - `git push` 被拒绝（`rejected`）→ 通常是远端有你本地没有的提交（比如你在 GitHub 网页上直接改过文件）。先执行 `git pull --rebase` 再 `git push`。
> - Vercel 显示构建失败 → 点进那条部署记录，看日志红字，对照第八部分。最常见的原因是本地忘了先 `pnpm run build`，出现了类型错误。
> - 推送成功但网站看起来没变 → 见 6.2。

### 6.2 为什么有时候「网站看起来没变」——Service Worker 的版本提示

本项目的 PWA 配置里用的是 `registerType: 'prompt'`（见 `vite.config.ts`）。它的行为是：

- 新版本部署后，**已经打开或已经安装**的旧版本**不会**被静默替换。
- 后端的 Service Worker 会进入「等待中」状态，界面上会出现一个提示，大意是 **「新版本已就绪」**（`src/vite-env.d.ts` 里也记录了这个提示的用途）。
- 用户点「刷新/更新」之后，新版本才生效。

这是**故意设计**的：对一份研究纲领来说，「你正在阅读的是哪个版本」必须是明确的，不能悄悄换掉。

**所以：如果你自己测试时觉得「改了但没变」，先刷新页面，看有没有那个「新版本已就绪」的提示，点一下它。** 或者按 F12 → Application → Service Workers → 勾 **「Update on reload」**，再刷新。

### 6.3 为什么 `vercel.json` 要设置那些 `Cache-Control`（背景知识）

Vite 官方文档给部署者的建议里包括两点（[Vite 构建文档](https://vite.dev/guide/build)）：

1. **给 HTML 文件设置 `Cache-Control: no-cache`**——否则用户可能长期拿到旧页面，而 `index.html` 里引用的 JS 文件名已经变了，就会出现白屏。
2. 关注 **`vite:preloadError`** 事件——它用于处理「用户手上是旧页面，而你刚部署了新版本，导致他请求的旧 JS 文件已经不存在」这类情况。

本项目的 `vercel.json` 里那几段 `headers`（尤其是 `sw.js` 和 `manifest.webmanifest` 的 `max-age=0, must-revalidate`，以及带哈希的 `assets/` 一年强缓存），就是为了把这两类问题在**服务器层面**提前挡掉：带哈希的资源可以放心长期缓存，而「入口类文件」（SW、清单）每次都必须校验。

**这就是为什么不要随手删掉 `vercel.json` 里的 `headers` 段落。**

## 第七部分 自定义域名（可选）

**先说结论：现在不要买域名。** 先用免费的 `.vercel.app` 网址，把第五部分全部验证通过，稳定运行一两周之后，再考虑这一步。

### 7.1 两种域名的区别

| 类型 | 例子 | 费用 |
| --- | --- | --- |
| Vercel 默认域名 | `https://immortality-program.vercel.app` | **免费**，HTTPS 自动开启 |
| 自定义域名 | `https://你的域名.com` | **要花钱**。钱是付给「域名注册商」的，Vercel 不卖域名，Vercel 这边不额外收费 |

### 7.2 如果将来真的要加，步骤是这样

1. 先在一个域名注册商那里买好域名（任何一家都行）。
2. 在 Vercel 控制台：进入你的项目 → **「Settings」** → **「Domains」** → 输入你的域名 → 点 **「Add」**。
3. Vercel 会显示**你这个域名需要配置的 DNS 记录**。**一定要用你自己面板上显示的那一行数值**（[添加域名文档](https://vercel.com/docs/domains/working-with-domains/add-a-domain)）。
4. 去你的域名注册商后台，找到 **「DNS 解析 / DNS Records」** 页面，按下面的规律添加记录（[DNS 记录管理文档](https://vercel.com/docs/domains/managing-dns-records)）：

   | 你要绑定的地址 | 记录类型 | 怎么填 |
   | --- | --- | --- |
   | 主域名（`example.com`，不带 www） | **A** 记录 | Host/Name 处通常留空或用 `@`；Value 填 Vercel 面板上给你看的那个 IP |
   | 子域名（`www.example.com`） | **CNAME** 记录 | **Name 处只填前缀**，也就是填 `www`（**不要**填完整的 `www.example.com`）；Value 填 Vercel 面板上给你看的那个值 |

5. **三条铁律**：
   - **绝对不要**使用从网上文章或教程里抄来的 IP 地址，只用**你自己的 Vercel 面板**里显示的值。
   - **同一个主机名，绝对不要同时建 A 记录和 CNAME 记录**，这会让解析互相冲突。
   - **DNS 生效最多可能需要 24 小时**（通常几分钟到一小时）。等的时候不用反复改设置。

6. 配好后回到 Vercel 的 Domains 页面，等它显示绿色的 **「Valid Configuration」**。HTTPS 证书也会由 Vercel 自动签发。

> **如果出错了**：
> - Vercel 一直显示 **「Invalid Configuration」** → 最常见的原因是 Name 字段填了完整的域名（应该只填前缀），或者记录类型选错了（主域名用 A、子域名用 CNAME）。
> - 域名能打开但报证书错误 → 等 10～30 分钟让证书签发完成，再刷新。
> - **不要同时保留默认的 `.vercel.app` 和自定义域名做重复内容**——如果想统一，在 Domains 页面里把一个设成跳转到另一个即可。

## 第八部分 常见报错排查

**通用技巧：把报错信息的第一行（不是最后一行）复制下来，去搜索引擎搜，或者交给 AI 助手。** 最后一行通常只是「命令退出码 1」这种结果，不是原因。

### 8.1 报错对照表

| 报错内容 | 原因 | 解决办法 |
| --- | --- | --- |
| `npm.ps1 cannot be loaded because running scripts is disabled on this system` / `PSSecurityException` / `FullyQualifiedErrorId : UnauthorizedAccess` | PowerShell 默认执行策略是 `Restricted`，禁止运行脚本（[Microsoft Learn](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies)） | 在 PowerShell 里运行 `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser`，用 `Get-ExecutionPolicy -List` 确认。**不需要管理员权限**。或者改用命令提示符（cmd），或把命令写成 `npm.cmd install` |

| `ERR_PNPM_TARBALL_INTEGRITY` | 下载到的包内容和锁文件里记录的哈希对不上，最常见的原因是**某个 registry 镜像重写（重新打包）了 tarball**。pnpm 把完整性不匹配当作硬错误（[pnpm 错误手册](https://pnpm.io/errors)） | 打开仓库根目录的 `.npmrc`，**删掉里面带 `registry=` 的那一行**（只保留 `node-linker=hoisted`，见 1.8）。镜像配置只保留在自己电脑的用户级 `%USERPROFILE%\.npmrc` 里 |
| `You are using Node.js 20.18.0. Vite requires Node.js version 20.19+ or 22.12+` | 本机 Node.js 版本低于 Vite 8 的要求（见 1.3） | 安装 **Node.js 22 LTS**（或 20.19+）后重开终端，再运行 `pnpm run build` |
| `Cannot find package 'rolldown'` 或 `spawn EPERM`（仅本机出现） | 依赖安装不完整，或本地安全软件/沙箱限制了子进程 | 删掉 `node_modules` 文件夹后重新运行 `pnpm install`。`.npmrc` 里的 `node-linker=hoisted` 就是为规避这类解析问题而设的 |
| `Vite 8 requires Node 20.19+`（在 Vercel 上） | Vercel 项目的 Node.js Version 被手动改成了 20.x 且低于 20.19 | 到 Settings → Build and Deployment → **Node.js Version** 改回默认（或选 22.x） |
| Vercel 构建日志：`Could not find a package.json` / `No package.json found` | Root Directory 设置不正确，Vercel 在错误的那一层找 `package.json` | 见 4.4 的两种情况，把 Root Directory 改成正确值（`package.json` 所在的相对路径，或留空），**Save** 之后重新部署一次（该设置只对下一次部署生效） |
| 深链接（例如 `/protocols/p01`）打开是 404 | `rewrites` 规则没生效 | 检查三件事：① `vercel.json` 必须在**项目根目录**（和 `package.json` 同一层，不能在 `dist/` 里）；② Root Directory 没填错；③ 改动已经 `git push` |
| `fatal: remote origin already exists` | 你已经用 `origin` 这个名字加过远端了，重复执行了 `git remote add` | 改用 `git remote set-url origin https://github.com/你的用户名/你的仓库名.git` 来直接改地址（想先确认当前地址，用 `git remote -v`） |
| `Updates were rejected because the remote contains work that you do not have locally` | 远端仓库不是空的——很可能创建仓库时勾了 **「Add a README file」**，GitHub 替你先生成了一次提交，于是两边历史不相关 | 最简单：**把这个仓库删掉重建一个完全空的**（GitHub 仓库 → Settings → 拉到底 → **Delete this repository**），然后重新按第三部分推送。想保留现有仓库的话，可以在**确认 GitHub 上没有任何你需要的内容**后执行 `git pull origin main --allow-unrelated-histories`，把两边合并，解决冲突后再 `git push` |

| 推送时反复要求输入用户名密码，或报 `Authentication failed` | GitHub 已取消密码认证；凭据没被记住，或缓存了旧凭据（[GitHub 认证文档](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github)） | 优先用 Git Credential Manager 的浏览器登录（3.4 路线 A）。手动路线用 Personal Access Token 当密码（3.4 路线 B）。如果缓存的旧凭据有问题：开始菜单搜「凭据管理器」→「Windows 凭据」→ 删除 `git:https://github.com` 后重试 |
| Vercel 构建日志里出现 `pnpm/6.x.x` 之类的老版本号 | 在某个地方把 `pnpm install` 填成了 Install Command 覆盖项。Vercel 会因此使用该包管理器**最老的可用版本**（[Vercel 包管理器文档](https://vercel.com/docs/package-managers)） | 把 Install Command **清空**（导入页或 Settings → Build and Deployment 里），只靠提交的 `pnpm-lock.yaml` 让 Vercel 自动识别，然后重新部署 |
| 网站能打开但样式全丢 / 图标 404 / 白屏 | 通常是资源路径不匹配（例如错误地改了 `base`），或缓存里混了旧版本 | 确认 `vite.config.ts` 里 `base` 是 `'/'`（部署在 Vercel 根域名时就是它）。再按 F12 → Console 看有没有红色的 404 请求；按 Ctrl+F5 强制刷新清缓存 |
| 手机上打开是空白 / 一直转圈 | 网络问题（中国大陆访问 Vercel 可能不稳定），或离线缓存首次未完成 | 这一点 Vercel 官方也承认（[Vercel 官方说明](https://vercel.com/kb/guide/accessing-vercel-hosted-sites-from-mainland-china)）。换 Wi-Fi/流量重试，或考虑第九部分的备选方案 |

### 8.2 怎么把报错发给我（你的 AI 助手）

复制的时候请包含这三样：

1. **你在哪个终端、输入了哪条命令**（例如「在 PowerShell 里输入 `pnpm run build`」）。
2. **从报错第一行开始，到结束的完整内容**（不要只复制最后一行）。
3. **项目的哪个文件在哪一行**（报错里通常有 `文件路径:行号`，例如 `src/content/posts.ts:193`）。

只发一句「报错了」是没法定位问题的。

## 第九部分 换成 GitHub Pages（备选）

**什么时候考虑这条路**：如果中国大陆的读者访问 `.vercel.app` 体验太差，或者你不想依赖 Vercel 的免费额度规则。GitHub Pages 也可以用，但**它对本项目来说要付两部分代价**。

### 9.1 代价一：必须修改 `base`

Vercel 部署在**自己域名的根目录**，所以 `base` 是 `/`。而 GitHub Pages 上的「项目页」地址形如 `https://你的用户名.github.io/你的仓库名/`，网站运行在一个**子路径**下。

这时必须把 `vite.config.ts` 里的

```text
base: '/',
```

改成（把 `你的仓库名` 换成真实仓库名）：

```text
base: '/你的仓库名/',
```

否则所有 CSS/JS 请求都会指向 `https://你的用户名.github.io/assets/...` 而 404，页面会白屏或完全没有样式。

### 9.2 代价二：离线和安装功能会退化

本项目在 `vite.config.ts` 里以 `/` 为作用域注册 Service Worker。但在 GitHub Pages 的项目页下：

- `sw.js` 实际位于 `/你的仓库名/sw.js`，**不再是站点根路径**下的 `/sw.js`；
- 于是它**无法再拥有站点根作用域**（一个 Service Worker 的作用域最多只能覆盖它自己所在的目录及其子目录）；
- 结果是：**离线缓存和「安装成 App」的行为都会明显退化或失效**（这也会影响 PWA 安装提示的出现）。

如果你能接受「只是一个普通网站，离线/安装功能不再保证」，那么 GitHub Pages 是可行的。

### 9.3 代价三：需要额外的工作流文件

GitHub Pages 不会像 Vercel 那样读 `vercel.json` 自动构建，你需要：

1. 在项目里新建一个 `.github/workflows/deploy.yml` 文件（这是 GitHub Actions 的「自动构建并发布」脚本）。
2. 到仓库 → **「Settings」** → **「Pages」** → 把 **「Source」** 设为 **「GitHub Actions」**。
3. 之后每次推送 `main` 分支，Actions 会自动构建并发布。

> **⚠️ 重要：不要手打 workflow 文件里的版本号和 commit SHA。**
> 请到 **Vite 官方文档的「Deploying a Static Site」页面里的 GitHub Pages 小节**，**原样复制**它当前给出的 workflow 配置（[Vite 静态部署文档](https://vite.dev/guide/static-deploy)）。因为这个文件里引用的 Action 版本号会随时间更新，抄一份过期的很容易构建失败。

### 9.4 小结

| | Vercel | GitHub Pages |
| --- | --- | --- |
| 配置文件 | 已有 `vercel.json`，**开箱即用** | 需要新建 workflow + 改 `base` |
| 深链接（SPA 路由） | 已用 `rewrites` 解决 | 需要额外处理（Pages 对 SPA 回退支持有限） |
| PWA 离线/安装 | **完整可用** | 明显退化 |
| HTTPS | 自动 | 自动 |
| 中国大陆访问 | 可能慢/不稳定 | 通常比 Vercel 更稳定，但仍可能不稳定 |
| 费用 | 免费（Hobby，有用途限制） | 免费 |

**结论**：先用 Vercel。只有在你明确需要「更稳的国内可达性」，并且能接受 PWA 功能退化时，才切换。

### 最后的几个提醒

1. **`.npmrc` 要留着一个，但里面绝不能有 `registry=`。** 项目根目录的 `.npmrc` 只应包含 `node-linker=hoisted`（原因见 1.8）。
2. **不要提交 `node_modules/` 和 `dist/`。** `.gitignore` 已经帮你挡住了，别去手工加。
3. **不要手改 `vercel.json` 里的 `rewrites` 和 `headers`**，除非你清楚自己在干什么。它们解决的是「深链接 404」和「Service Worker / 安装 / 缓存」这几类很隐蔽的问题。
4. **`pnpm-lock.yaml` 必须一直在仓库里。** 它决定了 Vercel 用什么包管理器、装哪个版本。
5. **每次改完先本地 `pnpm run build`。** 本地过不了，线上一定过不了——本地报错比线上构建日志好读一万倍。
